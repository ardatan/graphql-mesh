# Schema registry

A **schema registry** stores **subgraph** and/or **supergraph** GraphQL SDL, versions it, and lets
gateways (or CI) pull the schema they should run. Examples: Hive schema registry, Apollo GraphOS,
and equivalents. Mesh publishes **Federation-compatible subgraph SDL** -- generated or hand-written
-- with the same Compose -> publish UX.

| Piece      | Role                                                      |
| ---------- | --------------------------------------------------------- |
| Publish    | Push subgraph SDL after Compose                           |
| Distribute | Gateway fetches supergraph / subgraph set                 |
| Optional   | Gateways can also take a Compose output **file** directly |

A registry is **not** a gateway, **not** a transport, and **not** Mesh Compose -- it sits **beside**
composition in the stack ([Architecture](/v2/architecture)).

## Short example

1. Compose subgraphs (loader + hand SDL) -- same pipeline for both ([Composition](/v2/compose)).
2. Publish each **subgraph** SDL to the registry (same CLI UX whether the SDL came from
   `loadSqlSubgraph` or a checked-in `.graphql`).
3. Point <ApiRef name="hive-gateway" /> (or Apollo Router for Connect-only) at the registry
   supergraph -- or at a local Compose file for local dual-run / CI.

### Edge cases

- **Connect vs Mesh protocols:** publishing does not change dual-run rules. A registry supergraph
  with `@sql` / `@protobuf__rpc` still needs Hive Gateway; Connect-only graphs can pull into Apollo
  Router.
- **`@composeDirective`:** Mesh / Connect directives must be composed into the published SDL or the
  gateway will not see them -- loaders usually stamp this
  ([Directives](/v2/reference/directives#federation)).
- **Join-only subgraphs** (FHIR `reference-resource.graphql`): valid registry citizens with `@key`
  stubs and no root Query.
