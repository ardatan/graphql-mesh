## I have Apollo Router but a SQL subgraph -- what do I do?

Apollo Router executes **HTTP/REST Connectors** (`@connect` / `@source`) from composed SDL. It does
**not** execute Mesh protocol directives such as `@sql`, `@protobuf__rpc`, or `@mongo`.

Pick one:

1. **Hive Gateway as the supergraph** for the full graph (SQL + anything else) --
   [Serve Supergraph: Hive Gateway](/v2/serve/hive-gateway).

```bash
mesh-compose -o supergraph.graphql
hive-gateway supergraph
```

2. **Hive Gateway subgraph proxy**: run the SQL subgraph on Hive Gateway; point Apollo Router (or
   another gateway) at that subgraph URL for Federation --
   [Serve Subgraph](/v2/serve-subgraph#hive-gateway-as-a-subgraph) /
   [Architecture: patterns](/v2/architecture#patterns).

```bash
mesh-compose --subgraph chinook -o chinook-subgraph.graphql
hive-gateway subgraph chinook-subgraph.graphql
# Apollo Router (or another gateway) uses this subgraph URL in its supergraph
```

3. **`buildSubgraphSchema`**: host the SQL subgraph SDL on Yoga (or any GraphQL server) as a
   Federation peer -- [buildSubgraphSchema](/v2/guides/build-subgraph-schema).

```bash
mesh-compose --subgraph chinook -o chinook-subgraph.graphql
npx tsx subgraph-server.ts # Yoga + buildSubgraphSchema loading that file
```

Same answer for other non-Connect protocols (Protobuf, Mongo, Neo4j, binary Thrift, ...).
Connect-only slices can still dual-run on Apollo Router beside a Hive-served Mesh surface --
[Music Store Example](/v2/examples/music-store).

## Do I need Hive Gateway if everything is Connect?

No. For Connect-compatible supergraphs you can serve on **Apollo Router**, **Hive Gateway**, or both
(dual-run). Hive Gateway remains preferred when any Mesh protocol transport is in the supergraph.

```bash
mesh-compose -o supergraph.graphql
hive-gateway supergraph
./router --supergraph supergraph.graphql
```

See [Serve Supergraph](/v2/serve) / [Apollo Router](/v2/serve/apollo-router).

## When should I Serve Subgraph instead of Serve Supergraph?

**Serve Supergraph** = one gateway process runs the composed graph. That is the default.

```bash
mesh-compose -o supergraph.graphql
hive-gateway supergraph
```

**Serve Subgraph** when you need a **standalone Federation subgraph URL**: foreign router / mixed
fleet, independent deploy, subgraph smoke tests, or code resolvers mixed with Mesh directives.

```bash
mesh-compose --subgraph chinook -o chinook-subgraph.graphql
hive-gateway subgraph chinook-subgraph.graphql
```

Details: [Serve Subgraph](/v2/serve-subgraph).

## Hive Gateway subgraph vs `buildSubgraphSchema` -- which?

| Choice                                                                 | Prefer when                                                                                          |
| ---------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------- |
| [Hive Gateway subgraph](/v2/serve-subgraph#hive-gateway-as-a-subgraph) | You already run Hive; same transport registration as supergraph serve; ops stay on Hive Gateway      |
| [`buildSubgraphSchema`](/v2/guides/build-subgraph-schema)              | You want Yoga / Apollo Server / Mercurius / any GraphQL HTTP stack; or custom `resolvers` beside SDL |

Both produce a Federation subgraph peer. Neither replaces [Composition](/v2/compose).

## How do I add a custom `@lookup` resolver?

Stamp Federation draft `@lookup` on an entity entry field that returns **one object**, then pass a
matching resolver into `buildSubgraphSchema({ resolvers: { ... } })`. Directive-driven fields still
come from the SDL. Use Type Merging `@merge` only for **list / batch** entry fields.

- [Serve Subgraph: resolvers for `@lookup`](/v2/serve-subgraph#resolvers-for-lookup)
- [Directives: @lookup](/v2/directives#lookup) / [Directives: @merge](/v2/directives#merge)
- [buildSubgraphSchema](/v2/guides/build-subgraph-schema)

## Generate, Generate-then-edit, or Hand-write?

| Path                                               | When                                                                       |
| -------------------------------------------------- | -------------------------------------------------------------------------- |
| [Generate](/v2/paths/generate)                     | Bootstrap from OpenAPI, SQL, Mongo, protobuf, ... and read the emit        |
| [Generate-then-edit](/v2/paths/generate-then-edit) | Emit with a loader config, then switch to `schema:` and own the `.graphql` |
| [Hand-write](/v2/paths/hand-write)                 | Author Connect / protocol / Federation SDL from scratch (human or AI)      |

All three produce subgraph SDL that Compose, registries, and `buildSubgraphSchema` accept the same
way. Overview: [Build your Subgraph](/v2/paths/generate).

## How do I Generate from the CLI?

Put loaders in `mesh.config.ts` as `export const composeConfig`, then:

```bash
mesh-compose --subgraph chinook -o chinook-subgraph.graphql
```

That **is** the Generate emit surface (not `.meshrc`). Full compose + serve:

```bash
mesh-compose -o supergraph.graphql
hive-gateway supergraph
```

Concrete configs: [Generate](/v2/paths/generate). After you edit the file, switch that subgraph to
`schema: './….graphql'` and re-compose -- shell walkthrough:
[Generate-then-edit: two configs](/v2/paths/generate-then-edit#two-configs).

## Automatic transform or edit the SDL by hand?

| Approach                              | When                                                                                          |
| ------------------------------------- | --------------------------------------------------------------------------------------------- |
| [Automatic](/v2/transforms/automatic) | Repeatable rename / filter / Federation stamp in `transforms: []` without touching `.graphql` |
| [By hand](/v2/transforms/by-hand)     | The edited schema is the source of truth (binders, keys, prune in the same file)              |

Skip transforms when Generate-then-edit or Hand-write already owns the public names.
[Transform Subgraph](/v2/transforms).

## Does Type Merging `@merge` replace Federation `@lookup`?

No. Prefer Federation draft `@lookup` / `@is` / `@internal` for **one-object** entity entry fields.
Keep Type Merging `@merge` for **list / batch** hops. They are not deprecated synonyms -- different
shapes. [Directives](/v2/directives#lookup).

## Can I use Mesh Compose with Hive / Rover composition?

Yes. Mesh Compose emits Federation-compatible subgraph / supergraph SDL. You can also publish
subgraphs to a [schema registry](/v2/concepts/schema-registry) and let Hive composition, Rover, or
another Federation composer build the supergraph. Mesh docs center on Mesh Compose; the SDL contract
is what matters. [Composition](/v2/compose).

## How is `@graphql-mesh/subgraph` different from `@apollo/subgraph`?

Same export name (`buildSubgraphSchema`), different jobs: Apollo's package Federation-wraps
**code-first** resolvers; Mesh's package makes **Mesh subgraph SDL** (transports + entity hops)
executable. Not drop-in replacements.
[buildSubgraphSchema: vs `@apollo/subgraph`](/v2/guides/build-subgraph-schema#vs-apollosubgraph).
